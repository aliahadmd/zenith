## Configuration System Overview

The Zenith Creator Platform uses **Wrangler** (Cloudflare's Workers CLI) as its primary configuration framework, with a single `wrangler.json` file serving as the central configuration manifest. The application follows Cloudflare Workers conventions for environment layering, secret management, and type-safe binding injection.

---

## Key Configuration Files

### Primary Configuration: `wrangler.json`
This is the single source of truth for all runtime configuration. It defines:

- **Worker metadata**: name (`zenith`), entry point (`src/worker/index.ts`), compatibility date/flags
- **Asset bindings**: Static assets served from `dist/client` with SPA fallback
- **Environment variables** (`vars`): Non-sensitive configuration like payment provider, platform fee basis points, Stripe mode/account ID, email settings, admin dashboard URL
- **Resource bindings**: D1 database (`DB`), R2 object storage (`STORAGE`), Send Email (`NOTIFICATION_EMAIL`)
- **Observability**: Logs, traces, sampling rates, source map uploads
- **Scheduled triggers**: Cron expression (`* * * * *`) for production environment
- **Environment overrides**: A `production` environment block that overrides vars, adds secrets requirements, and swaps resource IDs for production values

### Generated Types: `worker-configuration.d.ts`
Generated by `wrangler types` (invoked via `npm run cf-typegen`). This file provides TypeScript interfaces for:
- `Cloudflare.Env`: All bindings available at runtime
- `Cloudflare.ProductionEnv`: Production-specific bindings including required secrets
- `NodeJS.ProcessEnv`: Maps worker vars to Node.js `process.env` for tooling compatibility

Developers must regenerate this file after modifying `wrangler.json` to maintain type safety.

### Build Tooling Configuration
- **`vite.config.ts`**: Integrates `@cloudflare/vite-plugin` for unified dev/build, TanStack Router for file-based routing, and Tailwind CSS. Defines path alias `@/` → `./src/react-app`.
- **`drizzle.config.ts`**: Database migration config reading credentials from `process.env.CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID`, `CLOUDFLARE_D1_TOKEN` — these are external to wrangler and used only for local migration tooling.
- **`vitest.config.ts`**: Test configuration using `@cloudflare/vitest-pool-workers` with reference to `wrangler.json` for test environment bindings.
- **`tsconfig.json`**: Project references pattern splitting into `tsconfig.app.json`, `tsconfig.node.json`, `tsconfig.worker.json`.

### Agent Configuration: `agents/openai.yaml`
Minimal interface metadata for AI agent tooling — not part of the application runtime configuration.

## Architecture and Conventions

### Environment Layering Strategy

The configuration uses a two-tier environment model:

1. **Default environment** (lines 34–65 in `wrangler.json`): Local development defaults with placeholder/local resource IDs (`zenith-local-db`, `zenith-local`). Secrets are optional (`BETTER_AUTH_SECRET?`, `STRIPE_API_KEY?`).

2. **Production environment** (`env.production`, lines 67–113): Overrides with production resource IDs, real URLs, and **required secrets** (`BETTER_AUTH_SECRET`, `STRIPE_API_KEY`, `STRIPE_WEBHOOK_SECRET`).

Deployment targets the production environment via `CLOUDFLARE_ENV=production` set in npm scripts (`deploy:production`, `build:production`, `dry-run:production`).

### Secret Management

Secrets are **never stored in `wrangler.json`**. Instead:
- The `secrets.required` array in the production environment declares which secrets must be set before deployment
- Secrets are injected at deploy time via `wrangler secret put <NAME>` or CI/CD pipeline
- The generated `worker-configuration.d.ts` marks secrets as optional in the default `Env` but required in `ProductionEnv`

### Runtime Binding Access Pattern

Bindings are accessed through Hono's context `c.env` typed as `Env`:

```typescript
// In src/worker/middleware/auth.ts
const auth = createAuth(c.env, new URL(c.req.url).origin)
const db = createDb(c.env.DB)
```

Configuration values are read directly from the env object with fallback defaults:

```typescript
// In src/worker/lib/payments/config.ts
const raw = (env as PaymentEnv).PLATFORM_FEE_BPS ?? '1000'
const key = (env as PaymentEnv).STRIPE_API_KEY
```

### Validation at Access Time

Rather than validating configuration at startup, the codebase validates individual config values when they are accessed. The `src/worker/lib/payments/config.ts` module exports getter functions that throw `PaymentConfigurationError` if required values are missing or invalid:

- `getStripeApiKey(env)`: Validates key exists and starts with `sk_test_` or `rk_test_`
- `getStripeMode(env)`: Enforces `test` mode only
- `getExpectedStripeAccountId(env)`: Validates account ID starts with `acct_`
- `getStripeWebhookSecret(env)`: Ensures webhook secret is configured
- `getStripeSandboxConfiguration(env)`: Composite validation calling all above

This deferred validation pattern means misconfiguration surfaces at first use rather than at boot.

### Scheduled Task Configuration

The worker exports a `scheduled` handler that receives `env` and `controller.scheduledTime`. Two maintenance tasks run on the cron schedule defined in `wrangler.json`:
- `processDueSchedules(env, scheduledTime)` — publishes scheduled content
- `processMembershipMaintenance(env, scheduledTime)` — processes membership renewals/expirations

## Rules Developers Should Follow

1. **All runtime configuration lives in `wrangler.json`**. Do not add `.env` files for worker-side configuration. The `.gitignore` explicitly excludes `.env.*` files, and the codebase has no dotenv integration.

2. **Regenerate types after config changes**. After modifying `wrangler.json`, run `npm run cf-typegen` to update `worker-configuration.d.ts`. This ensures TypeScript catches missing or mistyped bindings at compile time.

3. **Use `wrangler secret put` for sensitive values**. Never commit API keys, webhook secrets, or auth secrets to version control. Declare them in `secrets.required` in the appropriate environment block.

4. **Access bindings through `c.env` in route handlers**. The `HonoEnv` type in `src/worker/middleware/auth.ts` defines `Bindings: Env`, making `c.env` properly typed throughout the request lifecycle.

5. **Use getter functions for validated config access**. For payment configuration and other critical settings, use the exported getters from `src/worker/lib/payments/config.ts` rather than reading env values directly. This ensures consistent validation and error messages.

6. **Local migrations require separate env vars**. The `drizzle.config.ts` reads `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_DATABASE_ID`, and `CLOUDFLARE_D1_TOKEN` from `process.env`. These are tooling-only variables, not runtime bindings. Set them in your shell or IDE environment for local migration commands.

7. **Deploy with `CLOUDFLARE_ENV=production`**. The npm scripts handle this automatically (`npm run deploy`, `npm run deploy:production`). Direct `wrangler deploy` calls without the environment flag will deploy to the default (local) environment.

8. **Test configuration uses wrangler.json**. The vitest pool workers plugin reads `wrangler.json` directly, so tests run with the same bindings as local development. No separate test configuration file is needed.
