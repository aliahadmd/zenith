## Why This Matters

`POST /api/auth/otp/request` accepts a valid email, stores a new OTP, and sends
an email without a request-rate guard. `OTP_MAX_ATTEMPTS` only constrains code
verification, not outbound delivery. A throttled request must return before it
writes D1 data or sends an email.

## Steps

### Step 1: Add two Worker rate-limit bindings

Add matching `ratelimits` arrays at top level and within `env.production`,
because named-environment binding arrays do not inherit from top level.

- `OTP_EMAIL_RATE_LIMITER`: 3 requests per 60 seconds per normalized-email fingerprint.
- `OTP_IP_RATE_LIMITER`: 10 requests per 60 seconds per client IP.

Use unique positive integer namespace IDs not used by another Worker in the
same account. Do not reuse an existing namespace unless shared counters are
intentional. Then run:

```sh
npm run cf-typegen
npx tsc -b --pretty false
```

**Verify**: `worker-configuration.d.ts` exposes both bindings in local and
`ProductionEnv` types, and TypeScript exits 0.

### Step 2: Reject rate-limited requests before D1 or email work

In `src/worker/routes/auth.ts`, add a small auth-route helper that:

1. Receives the already normalized email and request.
2. Produces a deterministic SHA-256 email fingerprint; never use or log raw
   email as a rate-limit key.
3. Reads `CF-Connecting-IP`, using a stable `unknown-client` fallback in tests.
4. Calls both bindings and rejects when either returns `{ success: false }`.
5. Returns the established JSON error shape with status `429`, code
   `rate_limited`, a generic retry message, and `Retry-After: 60`.

Call the helper at the top of the OTP request handler, before `storeSignInOtp`
and `sendOtpEmail`. Do not reveal whether an email has an account.

**Verify**: code review confirms a rejected request writes no verification row
and invokes no email sender.

### Step 3: Add Worker integration coverage

Extend `src/worker/routes/auth.integration.test.ts` using its existing
`SELF.fetch`, migrations, and helpers. Use a fixed `CF-Connecting-IP` header.
Cover:

- Requests inside both limits retain the current success response.
- The next request returns 429, `error.code === 'rate_limited'`, and
  `Retry-After: 60`.
- A different IP cannot bypass the per-email cap.
- Different emails on one IP still hit the IP cap.
- Rejections have no account-existence signal.

Configure rate-limit bindings using the supported Workers Vitest pool mechanism;
do not weaken production code for test-only behavior.

**Verify**:

```sh
npx vitest --run --config vitest.config.ts src/worker/routes/auth.integration.test.ts
```

Expected: existing and new assertions pass.


**Verify**: all commands exit 0 and dry-run output lists both limiter bindings
for `zenith-production`.
